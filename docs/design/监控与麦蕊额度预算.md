# 监控、Agent 与麦蕊日额度预算

> 对照日期：**2026-09-23**。与 [`API现状.md`](./API现状.md) §6.2–§6.5、§7.5 一致；实现入口见 `src/platform/scheduler.py`、`src/agents/watcher.py`、`src/market/clock.py`。
>
> **假设：** 单张证书 **日额度 B = 10 000 次**（每次 `MarketClient._get` 到 `api.mairuiapi.com` 计 1 次）。多证轮换见证书池文档，本文按「一张证一天」算账。

---

## 1. 目标

| 目标 | 含义 |
|------|------|
| **尽量用满** | 盘中监控、盘后扫描、Agent、工作台查询都在额度内可持续跑一整天 |
| **不要暴毙** | 避免上午就把 10 000 打光，下午 101 空表、监控全挂 |
| **可配置** | 用「预算分区 + 频率」推导该开哪些任务、扫描间隔多大 |

工作台侧 **P0–P3**（快刷 / 列预设 / 慢字段 TTL / 表级快照）已把「查询」从「每次全量 9N」拆开；**监控与 Agent 仍要单独算账**，且与墙钟调度叠加。

---

## 2. 谁在扣次数（本仓库现状）

| 来源 | 调度（默认） | 主要 HTTP |
|------|----------------|-----------|
| **墙钟** `clock-align` | 交易日 9–15 点 **每分钟**触发；同 **5 分钟档**内读档则 **不再打麦蕊** | 每档每用户约 `⌈N/20⌉` 次 `ssjy_more`（`clock_interval_sec` 默认 300） |
| **盘中监控** `schedule=session` | **每 5 分钟**（`scheduler`：`*/5`，9–15 点） | 每次 `run_watcher` 先跑 `_query_rows`（价+底顶 → `quote`+`bars`，`refresh_mode=cache`）；若开 **涨停/跌停** 则 **每次 +2**（`ztgc`/`dtgc` 全池，与 N 无关） |
| **盘后监控** `schedule=eod` | 每天 **20:20** 一次 | 同上 `_query_rows` + 各 EOD 任务按只调股东/资金/公告等 |
| **Agent** | 用户问答触发 | `quote` / `profile` / `finance` / `query_run` 等；`query_run` 已默认 `cache`，`company_profile` 等工具仍可能直连 |
| **工作台** | 手动 | 快刷 `quote`；查询 `cache`；全量 `full`+`force_live`（见 API现状 §6.5） |
| **固定杂项** | 启动/顶栏 | 探针约 3 次 `ssjy`；顶栏指数约 3 次/次 `loadBoard`（前端已 60s 缓存；快刷不再顺带拉指数） |

监控任务模板见 `src/agents/rules.py` 的 `TEMPLATE_SPECS`。盘中任务含：接近底部、接近减仓、涨停、跌停；盘后含：股东、资金、公司事件、公告/问董秘、复盘、龙虎榜、基金持股等。

## 3. 单次 `run_watcher` 成本（N = 自选只数）

### 3.1 每次都会跑的前置查询

`watcher` 对当前自选做一次 `QueryEngine.run`（列：现价、离底%、目标卖价、决策卡相关等），依赖 **`quote` + `bars`**，且为 **`refresh_mode=cache`**。

| 块 | 次/只（冷） | 命中缓存后 |
|----|-------------|------------|
| 现价 | 摊到 `⌈N/20⌉`/次 | 墙钟档内已有则 **0** |
| 日线（底顶） | 1 | `data/cache/bars_*` 长期 **0** |

盘中 **接近底部 / 接近减仓 / 涨跌停判断** 主要用这次 `_query_rows` 的结果，**不会**为每只再跑一整遍财务/股东。

### 3.2 盘中 session 额外

| 条件 | 每次扫描 HTTP |
|------|----------------|
| 开启 **涨停** | +1（`hslt/ztgc/{日}`） |
| 开启 **跌停** | +1（`hslt/dtgc/{日}`） |
| 两者都开 | **+2/次**（与 N 无关，但很费） |

### 3.3 盘后 eod（每只、冷启动量级）

P2 慢字段 TTL 命中后，当日重复扫描可接近 **0**（profile/holders/finance 24h，flow/indicators 1h）。

| 任务 `job_key` | 约 HTTP/只（冷） | TTL 后 |
|----------------|------------------|--------|
| `holders-change` | 2 | 24h 内 ≈0 |
| `capital-flow` | 1～2 | flow 1h 内 ≈0 |
| `corp-events` | 多只接口（分红/增发/解禁等） | 视快照对比，仍可能每日 1 轮 |
| `corp-disclosure` | 公告 + 问董秘 | 同上 |
| `limit-review` | 涨跌停表现 + 竞价 | 盘后 1 轮 |
| `fund-holding` | 基金持股 | 24h 内 ≈0 |
| `dragon-tiger` | **全市场 1 次** | 1/天 |

资讯/政策（`news`/`policy`）默认灰卡；命中时 `profile` 走监控侧 **cache TTL**（见 P3）。

## 4. 交易日自动化底数（默认全开、session 5min、N=10）

| 项 | 次/日（量级） |
|----|----------------|
| 现价档（墙钟+监控共用 5min 档，约 84 档/交易时段） | **~84 × ⌈N/20⌉** → N=10 约 **84** |
| 涨跌停池（2×每 5min 扫描） | **168**（固定，与 N 无关） |
| 日线冷启动（首日） | **+N**，之后 **≈0** |
| EOD 一包（首日冷缓存） | **~50～120**（取决于开启条数） |
| 探针 + 顶栏等 | **~50～200**（视是否常开页面） |

**N=10、慢字段 TTL 稳定后：** 自动化常 **~300～450/天**（其中 **168** 来自涨跌停池）。

**N=30：** 现价档约 **84×2=168**，池仍 **168**，EOD 按只增加 → 自动化常 **~600～900/天**（不含手动全量）。

**结论：** 1 万额度可以跑监控，但不能同时：**5 分钟全模板 + 大自选 + 频繁全量查询 + Agent 反复拉财务**。

---

## 5. 日预算分区（B = 10 000）

建议全天用到 **70%～85%**（**7 000～8 500**），留 **15%～30%** 给误点全量、Agent 加问、失败重试。

| 分区 | 建议上限 | 用途 |
|------|----------|------|
| 工作台 | **2 500～3 500** | 快刷/查询为主；全量 **≤5～10 次/日**（N=10 每次约 **90+**） |
| 盘中监控 | **2 000～2 500** | session + 墙钟现价 |
| 盘后监控 | **800～1 500** | 每日 1 次 eod + TTL |
| Agent | **800～1 500** | 控制轮次与工具数 |
| 缓冲 | **≥1 000** | 探针、指数、池接口、偶发全量 |

**按交易时段均摊（约 6.5h）：** 平均 **≈1 000 次/小时** 较安全；单小时 **>1 500** 时应减频或关池扫描。

## 6. 频率设计建议

### 6.1 盘中（`schedule=session`）

| 自选 N | session 间隔 | 涨停/跌停 | 说明 |
|--------|--------------|-----------|------|
| ≤15 | **5 min**（现默认） | 可都开 | 池 **168/日** 尚可接受 |
| 16～30 | **10 min** | 关其一或间隔 **15 min** | 池请求约减半 |
| >30 | **15 min** | 建议只开其一或改盘后核对池 | 池+现价占满预算 |

**优先省额度：** 降 **涨跌停池扫描频率** 或 **关闭池任务**，比缩小自选更有效（池是 O(扫描次数)，不是 O(N)）。

### 6.2 墙钟

- 与 `clock_interval_sec`（默认 **300s**）一致即可。
- 监控 `_query_rows` 在 **`force_live=false`** 且档内已有现价时，**同档后续扫描常为 0 现价 HTTP**。

### 6.3 盘后（`schedule=eod`）

- **每天 1 次**（现 **20:20**）合理。
- 任务按 **按需开启**；全开会把「首日冷启动」推到 **N×(2～8)** 量级。
- 依赖 P2：次日起股东/财务/flow 大量 **0 HTTP**，eod 常降到 **几十次/天**（N=10）。

### 6.4 Agent

| 策略 | 效果 |
|------|------|
| 问价 → 工具 **`quote`** | 约 `⌈k/20⌉`，k 为涉及只数 |
| 问基本面 → **`company_profile` / `finance_snapshot`** | 每只约 2～3；重复问仍可能扣网（工具未统一走 cache 时） |
| 要表 → **`query_run`** | 用 **cache**，避免默认全量列 + `full` |
| 单轮对话 | 建议 **≤4 次工具**、**≤5 只**；粗算 **50～150 次/轮** |

**示例：** 15 轮中等深度 × 80 次 ≈ **1 200/天**。

## 7. 两条日配方（N = 10）

### 配方 A：偏看盘（额度留给手动）

- Session **10 min**；只开 **接近底部 / 接近减仓**；**关涨跌停池**。
- EOD：**股东 + 资金 + 公告**。
- Agent **≤10 轮/天**。
- 工作台：**快刷为主**，全量 **≤3 次/天**。

**自动化约 200～400/天**；余下 **9 000+** 给查询。

### 配方 B：偏监控（用满但不爆）

- Session **5 min**；涨停+跌停 **都开**（**+168/天**）。
- EOD **全开**（首日 ~100，TTL 后 **~30～60/天**）。
- Agent **~15 轮/天**（~1 200）。
- 工作台：cache 查询 **~30 次** + 全量 **~5 次**（~500）。

**合计粗算 2 800～3 500/天**，余 **~6 500** 缓冲 —— 对 1 万证属健康区间。

## 8. 估算公式（自行代入）

记：

- `T` = 交易时段内 session 扫描次数（5min 间隔约 **84**；10min 约 **42**）
- `P_pool` = 2（涨跌停都开）/ 1 / 0
- `H_bars` = 首日约 **N**，之后 **0**
- `E_eod` = 盘后任务冷启动与 TTL 命中后的实耗（见 §3.3）
- `W` = 工作台手动
- `A` = Agent

```text
日总消耗 ≈
  T × ⌈N/20⌉                    # 现价档（墙钟与监控同档时近似）
+ T × P_pool                    # 涨跌停池（与 N 无关）
+ H_bars
+ E_eod(N, 任务清单, TTL)
+ W + A + 50                    # 工作台 + Agent + 探针/指数等
```

**约束：** 建议 **≤ 0.85 × B**；**> 0.95 × B** 时应：**关池 / 拉长 session / 减 EOD 任务 / 禁止习惯性全量更新**。

## 9. 与查询优化的关系（P0–P3）

| 期 | 对工作台 | 对监控/Agent |
|----|----------|----------------|
| P0 快刷/全量 | 刷新不再默认 `9N` | watcher 仍每次 `_query_rows`，但列少、非全量 |
| P1 看盘/研究 | 新用户默认少列 | 间接减 Agent `query_run` 列依赖 |
| P2 TTL `cache` | 查询少打慢字段 | **watcher `engine.run` 与 `query_run` 已用 cache**；EOD 次日省额度 |
| P3 表级快照 | 登录先快照 | 监控不读快照，仍按调度打网或 TTL |

**当前最浪费的两类（优先治理）：**

1. **涨跌停池每 5 分钟各 1 次**（固定 **168/天**）。
2. **工作台全量更新**（`full` + `force_live`，约 **`⌈N/20⌉ + 9N`**/次）。
